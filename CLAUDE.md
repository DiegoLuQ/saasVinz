This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**SaaSCrematorio V2** is a multi-tenant SaaS platform for crematory and funeral home management. It supports subdomain-based routing per tenant, RBAC, audit logging, pet memorials, partner/veterinary portals, and payment processing via Polar.sh.

`MEJORAS_SISTEMA.md` (repo root) holds the prioritized improvement plan with implementation status. Largest pending item: S-09 (apply migrations 014/018/020 in production — 020 is required before deploying the refresh-token backend).

### Full Stack (Docker Compose)
```bash
docker-compose up -d
```
Services (VPS deployment): backend (1 instance), frontend, pgAdmin, Redis (rate limiting), **postgres** (own container, `vinzer_postgres`, with a persistent named volume — defined in this compose file). The reverse proxy is **jwilder/nginx-proxy + acme-companion already running on the VPS** (integration via `VIRTUAL_HOST`/`LETSENCRYPT_HOST` env vars on the shared external network) — the compose file does not start its own proxy, but it does start and own its PostgreSQL. Postgres sits on an internal-only bridge network (`db_internal`), not the external reverse-proxy network — only `backend` and `pgadmin` can reach it. The backend still self-provisions (role + migrations) against it on boot via `entrypoint.sh`/`provision_db.sh`, exactly as before.

> **AI generation timeouts**: generating an illustration can take >60 s. Next's rewrite proxy is raised to 180 s (`experimental.proxyTimeout` in `next.config.ts`; default 30 s returns a 500 while the backend still finishes and consumes the attempt). In production nginx-proxy also needs `proxy_read_timeout 180s; proxy_send_timeout 180s;` (e.g. in `/etc/nginx/vhost.d/default`, then restart the proxy container), otherwise it cuts at 60 s.

> **Warning**: `app/core/client_ip.py` extracts the real client IP from `X-Forwarded-For` assuming the current proxy's behavior. If the reverse proxy ever changes (e.g. to Traefik/Caddy), re-validate that function — the 5/min login rate limit depends on it.

## Architecture

### Multi-Tenant Isolation
Tenant isolation is enforced at the **PostgreSQL level** via Row-Level Security (RLS). Before every query, `app.current_tenant_id` is set as a session variable; RLS policies use this to filter rows automatically. Admin operations bypass via `app.bypass_rls = 'true'`. See `backend/app/database.py` and `backend/app/core/tenant_context.py`.

### Subscription Plans & Module Tiers
**The database is the authoritative source for plans, not the seed scripts.** `backend/scripts/database/seed_plans.py` is the initial bootstrap but has drifted from current production values (notably prices, limits, and the Track plan which seed does not define). Always query `SubscriptionPlan` directly when reasoning about caps.

**Track** is the entry paid tier («Controla cada servicio. Mantén informada a cada familia.»): $29.900, 25 orders/month, 2 users (created by the SuperAdmin), 0 partners, 10 services / 5 plans / 15 products, 0 monthly AI credits (can buy), no delete/export. **Pets and customers are NOT plan limits** (decision 2026-11-02): `max_pets`/`max_customers` stay in the table but nothing enforces or shows them (dashboard `limits.pets/customers.max` = 0 = unlimited; the clientes/mascotas/registro screens no longer block).

**Plan-exempt modules**: `PLAN_EXEMPT_MODULES` (`app/services/plan_features.py`: dashboard, perfil, configuracion) are never blocked by a plan's `allowed_modules`, so every plan reaches Configuración → General / Facturación / Notificaciones; the other Configuración tabs follow plan features (`CONFIG_TAB_FEATURES`) or modules (`CONFIG_TAB_MODULES`, Certificados) in `hooks/useCanOpen.ts`. `useCanOpen().canOpen(href)` (module + feature + config tab) hides/locks links to sections the plan lacks (onboarding card, «Comprar créditos», Generar todo). `ModuleRouteGuard`: a module outside the plan shows «Esta sección no está incluida en tu plan» + «Ver planes» (owners) instead of redirecting; a module the ROLE lacks still redirects.

Hard caps on `max_orders/services/plans/products` are enforced via `app/api/deps_limits.py` (`check_resource_limit`); `max_users` when the SuperAdmin creates a user; pets/customers are not limits (see above) and `max_partners` is not enforced in the backend. Module access per plan is checked via `allowed_modules` (JSON column). The `veterinarios` module is allocated in the data model but the B2B portal is incomplete (see "Próximamente" below).

To change plans: edit directly via admin endpoints or a migration script that updates the `SubscriptionPlan` rows. Do not assume `seed_plans.py` reflects reality.

### Domain Model: Workflow & Public Tracking
Each `CremationOC` carries two identifiers:
- `verification_code` (10-char alphanumeric, unique) — printed/displayed for human verification.
- `tracking_token` (secure token in `CremationDetails`) — used in the public tracking URL.

Public tracking endpoint: `GET /api/public/tracking/{tenant_slug}/{pet_name}/{tracking_token}` returns the full timeline (each `WorkflowStep` + `OrderEvidence`) without authentication. It also returns `pet_images` (up to 3 pet photos, main first, `_tracking_photos`), which the tracking page cross-fades every 5 s in the hero circle with dots to pick one. The family follows the service in real time via this link.

`WorkflowStep` is **tenant-configurable** — each crematory defines its own sequence of phases. Advancing a step typically requires `OrderEvidence` (photo + notes + operator signature). The frontend's `OperationDetailModal` is the operator's primary UI for this flow.

### Embeddable Widget (public API keys)
Tenants on **PRO/ULTRA** plans (`WIDGET_ALLOWED_PLANS` in `app/api/internal/integrations/services.py`) can embed a catalog/tracking widget on their own websites:
- Public API keys `pk_vinzer_live_*` per tenant (table `sys_tenant_api_keys`, migration 018). Keys are public by design — security relies on the `allowed_domains` whitelist validated against the `Origin` header, plus instant revocation via `is_active`.
- Public endpoints: `/api/public/widget/{catalog,products-services,tracking/*}` — rate-limited 60/min per API key (30/min for tracking) with ETag caching (`max-age=300`).
- Embeddable script is versioned: `frontend-saas/public/widget/v1.js` (+ `demo.html`). Treat its JSON contract as stable — third-party sites depend on it.

### RBAC: Roles & Permissions
8 roles defined: `admin`, `recepcion`, `operador_cremacion`, `contabilidad`, `marketing`, `auditor`, `operator`, `driver`. Plus `creator` (SuperAdmin, bypasses tenant scope).

Permissions are granular: `{module_key, action}` where action ∈ `{view, create, edit, delete}`. Enforced via `check_permission()` in `app/api/deps.py`. Frontend mirrors this via `usePermissions()` context and the `useFeatures()` hook for feature-flag gating.

Plan features (admin → Planes → "Configurar Características", `SubscriptionPlan.features`) sit inside modules. A missing flag = allowed (same as the Sidebar). Enforcement status:
- URL: `ModuleRouteGuard` + `featureForPath()` in `lib/tenant/moduleRoutes.ts` show "no incluida en tu plan" for the 11 gated sections (categorías, proveedores, repositorio, diseños/redes, emitir certificado, panel de trabajo, historial y cobros, veterinarios, comisiones, roles y módulos).
- API (`check_feature(key, default=True)` from `app/api/deps_features.py`): category/provider writes, RBAC tenant-config/toggle-module + `/auth/users/{id}/permissions`, commissions list (`comisiones:ver`) and pay/unpay (`comisiones:liquidar`), repository deletes; plus the older `certificados:generar_pdf`, `certificados:diseno`, `mascotas:memorial`. Shared reads (categories/providers list, `/ops-records/`, cremation lists, `/ops/board`, partner options) are intentionally NOT gated because other screens use them.
- CRUD flags (`clientes|mascotas:crear/editar/eliminar`, `servicios:crear/editar`, `ordenes:crear/editar/eliminar`): enforced inside `check_permission()` via `PLAN_ACTION_FEATURES` (rbac/router.py) **before** per-user overrides, so the plan is always the ceiling; mirrored in the frontend `PermissionContext` (`canCreate/canEdit/canDelete`). Product create/edit/delete use `check_feature` directly. The registro "Procesar" endpoints (`/submissions/{id}/create-customer|create-pet|create-services`) now require clientes/mascotas/ordenes create (they had no permission check at all).
- Also: `dashboard:metricas` hides the dashboard KPIs + monthly chart (frontend only, it's the tenant's own data); `operaciones:seguimiento:crear` gates the `/dashboard/operaciones/crear-seguimiento` route (its API is order creation = `ordenes:crear`); `configuracion:usuarios` gates editing / activating users (`PATCH /auth/users/{id}` and `/toggle`; the list stays readable).
- Modal registry modules must be existing `allowed_modules` keys (a feature whose module is off is forced off), so new sections live under existing modules: Documentos (`certificados:generar_pdf`, `repositorio`, `diseno` = Tarjetas de Homenaje, `redes` = Diseños para Redes IA, `generar_todo`), Configuración (`roles`, `usuarios`, `formulario`, `flujo`, `creditos_ia`, and Integraciones `integraciones:widget|formulario_incrustable|video_bienvenida`). Enforcement: `redes` → AI session/text/image/both, save illustration, save design (reads + digital-card upload stay open) + route/menu; `generar_todo` → `PUT /auto-documents`, `POST /auto-documents/runs`, registro panel, config tab (GET stays open); `formulario` → form-config/weight-pricing/form-video writes; `flujo` → workflow steps POST/PUT; `creditos_ia` → credit purchase/cancel; config tabs hidden via `TAB_FEATURES` in configuracion/page.tsx. Integrations read the flag through `app/services/plan_features.py` (`plan_has`/`tenant_has`), falling back to the old plan-name rule (widget/video PRO+ULTRA, embed ULTRA) when unset; migration `d1f3b5c7e896` stores those values explicitly.
- Removed from the modal because no such function exists: `pagos:registrar`, `veterinarios:solicitudes`, `configuracion:avanzada`, `operaciones:seguimiento:qr_publico` (family tracking is core to every plan). Their old keys may remain in `SubscriptionPlan.features` and are ignored. Every flag in `FEATURES_REGISTRY` (ManageFeaturesModal.tsx) is now enforced; add the enforcement whenever a new one is added.

### Subdomain Routing (Frontend)
`frontend-saas/src/middleware.ts` routes based on hostname:
- `admin.*` → `/admin` (SuperAdmin dashboard; guarded by `saasc_token` cookie)
- `app.*` → `/tenant` (tenant operations; the tenant is identified by JWT, not by a slug subdomain)
- `veterinary.*` → `/veterinary` (partner portal; guarded by `vet_token` cookie)
- `memorial.*` or the dedicated domain (`NEXT_PUBLIC_MEMORIAL_DOMAIN`, e.g. pawmemory.pet) → `/public`
- `track.*` → `/track` at the root (public search-by-code page); other paths → `/public`
- root / `www.` → `/vinzer` (marketing site)
- any other subdomain → redirect to root

For local dev, use `lvh.me:3000` (resolves to 127.0.0.1) with subdomains like `admin.lvh.me:3000`.

Each feature module under `backend/app/api/internal/` follows this pattern:

Modules: `admin`, `auth`, `catalog`, `crm`, `operations`, `creator`, `memorials`, `payments`, `partners`, `veterinary`, `common`, `integrations`.

### Authentication
- Access token: JWT (HS256), **60 min**, emitido en cookie **httpOnly** `saasc_token` por el backend en el login (viaja por el proxy same-origin de Next). El header `Authorization: Bearer <token>` sigue soportado y tiene precedencia (scripts/tests).
- Refresh token: opaco, rotatorio, **7 días**, cookie httpOnly `saasc_refresh` (path `/api/internal/auth`), hasheado SHA-256 en la tabla `sys_refresh_tokens` (migración 020). Reuso de un token ya rotado revoca todos los del usuario.
- Endpoints: `POST /api/internal/auth/login` (OAuth2PasswordRequestForm; setea cookies), `POST .../refresh` (rota; el frontend lo llama ante un 401 con single-flight en `lib/auth/token.ts`), `POST .../logout` (revoca + limpia cookies).
- `saasc_session` es un marcador NO-httpOnly (sin token) para que el cliente sepa "hay sesión" (`hasSession()`); el JWT no es legible por JavaScript.
- Protected endpoints usan `get_current_user()` de `backend/app/auth.py` (token desde header o cookie vía `get_token_from_request`).
- Portal veterinario: `vet_token` (cookie/localStorage legible, flujo antiguo) — pendiente de migrar al mismo patrón.
- `get_current_user` solo acepta tokens de sesión del panel (`role` ∈ `UserRole` y claim `tenant_id` presente; un usuario creator exige `role=creator` en el token): el mismo `SECRET_KEY` firma los tokens del portal veterinario y los enlaces de restablecer contraseña, cuyo `sub` es el id de otra tabla (antes una veterinaria con el mismo id que el SuperAdmin entraba como SuperAdmin).
- «Olvidé mi contraseña» (usuarios de crematorios, no el creator): `POST /api/internal/auth/forgot-password` (3/min, respuesta genérica) y `/reset-password` (enlace JWT 30 min, uso único por huella del hash, sube `token_version` y revoca los refresh tokens). Páginas `app.<dominio>/olvide-contrasena` y `/restablecer` (públicas: `isPublicAuthPath` en `lib/auth/token.ts` evita el bootstrap y la redirección por 401). URL de los enlaces: `TENANT_APP_URL` o `app.` + host de `FRONTEND_URL`.

### Public Registration Form (per-tenant config)
- Each tenant chooses which optional fields of the family form (`/public/[slug]/form`) are shown/required: `sys_tenants.form_config` (migration `d9a2c4e6f813`). Field catalog + defaults (= previous behavior) live in `backend/app/services/public_form_config.py`, mirrored in `frontend-saas/src/lib/publicFormConfig.ts`. Fixed fields: owner name/phone, pet name/species. `submit-form` enforces required fields server-side.
- Weight tiers (`srv_weight_pricing`, max 20) have a tenant-written "desde – hasta" range (e.g. 0–4, 4,1–7); a tier can't start before the previous one ends, and only the last may be open (`max_weight` NULL). The surcharge picks the first tier (by max) whose max covers the weight. Saved as a whole via `PUT /api/internal/maintenance/weight-pricing`. Same tiers drive the internal weight surcharge, the public form size picker and the plans catalog; prices go public only if `form_config.show_weight_prices`. On submit the backend writes the chosen tier text into `pet_data.size`. It also snapshots the tier price into `pet_data.weightTier.price`; the submission detail (`/dashboard/registros/{id}`) shows it as a "Recargo por peso" line and adds it to the total via `submission_weight_charge()` (older submissions without the snapshot use the current tier price). Creating the order from the submission stores that amount as `CremationFinancial.weight_price` and adds it to `total_price`. Order weight surcharge rule: with `weight` (kg) it is derived from the current tiers; without kg the saved `weight_price` is kept (backend expediente and `useOrderForm`), and the crematorium can edit or remove it in the order.
- **Precio por plan y peso** (`form_config.weight_pricing_mode = "table"`, default `"surcharge"`): instead of one surcharge per tier, each plan has its own final price per tier in `srv_plans.weight_prices` (`{"<tier id>": price}`, migration `f4c6e8a0b247`; empty cell = plan base price). No weight surcharge is added in this mode; special services never change with weight. Edited as a plans × tiers grid in Pesos y precios (`PlanWeightPriceTable.tsx`, API `GET/PUT /api/internal/maintenance/plan-weight-prices`; columns follow tier position, as tier IDs are reused by position). Helpers in `public_form_config.py` (`uses_price_table`, `tier_for_weight`, `plan_price_for_tier`, `submission_tier_id`): the public form snapshots the plan at its tier price (`weightTier.price` = 0), public services/catalog return `weight_prices` and tiers without price, `useTenantForm` / `PublicPlansCatalog` show the tier price, `useOrderForm` prices the plan line from the tier of the order's kg (`planPriceForWeight`).

### Deleting an order (scopes)
`DELETE /api/internal/cremations/{id}?scope=order|pet|all` (UI: `components/tenant/orders/DeleteOrderModal.tsx`, used in recepcion-pedidos list and order form; `delete-preview` returns `scopes` with availability/counts). `order` deletes only the order and its files (restores stock) and **never touches the pet's photos**. `pet` (only if the pet has no other orders; also needs `mascotas:delete`) runs `crm/pets/purge.py`: pet, its orders, memorials, web submissions, AI illustrations/designs/cards (`sys_template_exports`) and files no longer referenced; AI generations/credit sessions are kept as consumption history without images. `all` also deletes the customer (only if no other pets; needs `clientes:delete`).

Deleting a web registro is a **soft delete** (`app/services/submission_trash.py`, migration `e8a0c2d4f651`): `DELETE /api/internal/submissions/{id}` (and deleting its bell notification) sets `status='deleted'` + `deleted_at/deleted_by`, keeps data AND photos, removes the bell notification and hides it from the inbox, bootstrap and public tracking; processing endpoints answer 409. «Registros Formulario» (`/dashboard/registros`, `SubmissionsTable`; linked at the bottom of the bell menu) has tabs Pendientes / Eliminados (`GET /api/internal/submissions?status=deleted`); «Restaurar» = `POST /{id}/restore` → `pending` (or `processed` if it already has an order). Permanent delete = `DELETE /{id}?permanent=true`, admin/creator only and only from Eliminados (409 otherwise): `purge_submission` in `crm/pets/purge.py` deletes the row, its bell notification and its photos in R2 + `web_media_library` after the commit, keeping any photo still used elsewhere (`delete_unused_files` → `_still_referenced`, e.g. the pet created when it was processed); a processed registro keeps its customer/pet/order (the detail modal says so and points to deleting the order with scope `pet`). `scripts/cleanup_orphan_submission_photos.py` (dry run; `--apply`, `--tenant`) removes photos of registros deleted before this.

Deleting a pet from `/dashboard/mascotas` (`DELETE /api/internal/pets/{id}`, `PetDeleteModal`): a pet with orders returns 409 «tiene órdenes asociadas» (delete them from recepcion-pedidos, scope `pet`); without orders it purges the pet, its photos, memorials, submissions and AI images, plus its customer when it has no other pets and the user has `clientes:delete` (`delete-preview` returns `customer.deleted` and `photos`). Logic `app/services/form_funnel.py` (`is_official`, `resolve_form_id` = same `?form=` id/name matching as the public form, `record`, `report`); table `web_form_events` (migration `a5b7c9d1e246`, RLS): one row per tenant + form + anonymous session + kind + detail (ON CONFLICT DO NOTHING, the first time is kept → time between steps). Kinds: `open`, `step_view:<familia|angel|camino|recuerdos|resumen>`, `field_error:<field>`, `field_touch:<step>.<field>` (first change of each field per step; `changedFields` in `lib/formEvents.ts` maps inputs to fields, the draft restored on load and the auto-computed age don't count), `back:<step>`, `size_select`, `service_select`, `photo_add`, `welcome_video`, `souvenir_click` (entered the products catalog), `card_download` (downloaded the commemorative card on the success screen), `whatsapp_click`, `submit_click`, `submit_error`, `submitted`.
- Public: `GET /api/public/tenant/{slug}?form=` returns `track_form`; `POST /api/public/tenant/{slug}/form-events` {session_id, kind, detail, form} (120/min, always 204, invalid/other forms ignored). Frontend `lib/formEvents.ts` (session id in localStorage `vz_form_sid_<slug>_<form>`, reset after submit), wired in `useTenantForm` (`trackFormEvent`: open, step changes, validation errors, back, size/service/photos, submit) and the form page (video, WhatsApp, souvenir store; `CondolenceModal.onWatchVideo`).
- SuperAdmin: Comercial → «KPIs del catálogo» section «Formulario oficial: hasta dónde llegan» (`components/admin/catalog/OfficialFormFunnel.tsx`, `GET /api/internal/creator/catalog-funnel/form?date_from&date_to&tenant_id`): visits / sent / conversion, then the journey phase by phase (`phases`, `_phases()`): Inicio (opened, welcome message shown `welcome_shown`, video watched vs skipped among those offered `welcome_video_offer`/`welcome_video`; «only opened» = left here), each step the form uses (reached + %, median time, people who left there with their last field, actions of that phase `PHASE_ACTIONS`, fields filled, validation errors placed by `FIELD_STEP`, «pulsaron Enviar pero no se completó» in Resumen) and Enviado (card download, souvenir store, WhatsApp, end video `end_video`); per-tenant table, tenants without an official form. The older flat keys (`steps`, `abandon`, `clicks`, `field_errors`) are still returned. `CondolenceModal` reports `onShown(hasVideo)` / `onDismiss`. A session belongs to the period of its `open`. Test `tests/test_form_funnel.py`.

### Diagnóstico 360° (SuperAdmin, prospect crematoriums)
- Admin → Comercial → «Diagnóstico 360°» (`/dashboard/diagnosticos`, spec in `DIAGNOSTICO_360.md`): the SuperAdmin evaluates a prospect crematorium in 10 / 15 / 20 questions (wizard `/nuevo` with «?» help per question, local draft `vz_diag_draft`), gets the result and sends a PDF report. Tabs: Diagnósticos (list, status nuevo/contactado/demo/cliente/descartado), Preguntas (bank editor: options with %, «No aplica», modes, recommendation, Vinzer feature), Configuración (category weights = 100, levels, recommend/partial thresholds, plan rules, CTA link), Resumen (market averages per area).
- Tables `sys_diagnostic_categories` / `sys_diagnostic_questions` / `sys_diagnostics` + `sys_saas_config.diagnostic_config` (migration `a4c6e8f0b257`, seeds 10 categories + 20 questions; global, no RLS). Logic in `app/services/diagnostics.py`: category % = average of its answered questions, total = weighted by category over categories with answers (comparable across modes), «No aplica» excluded; answers stored as a snapshot (question/answer/% text) so editing the bank never changes old reports. Suggested plan (one): needs from the answers (weak C1/C10 → NORMAL, weak C3/C4 → Track, else NORMAL), raised to the smallest paid plan whose `max_orders` covers the monthly cremations (`paid_plans`/`capacity_plan`, `by_volume` + `needs_plan` in `suggested_plan`); price read live from `SubscriptionPlan`. Email match links `linked_tenant_id`. API `/api/internal/creator/diagnostics` (creator only).
- PDF built in the browser with `@react-pdf/renderer` (`components/admin/diagnostics/DiagnosticPDF.tsx`, `buildDiagnosticPdf.ts`: WebP logo → PNG via canvas, QR from a hidden `QRCodeCanvas`); «Enviar» posts it to `POST /{id}/send`, which emails it as an attachment (`send_action_email(attachments=…)`) and moves status nuevo → contactado.
- **Public self-diagnosis** `vinzer.cl/diagnostico` (`app/(public)/vinzer/diagnostico/`, `components/vinzer/diagnostico/DiagnosticoClient.tsx`; for Google/IG/TikTok traffic, use `?utm_source=`; linked from the Vinzer navbar «Diagnóstico gratis» and footer; SEO text below the form + FAQPage JSON-LD from `lib/vinzer/diagnosticoContent.ts`): the crematorium enters only business name + email (reCAPTCHA), picks a monthly-cremations range (`volume_ranges`, built from the paid plans' `max_orders`: «Hasta 25 / 26 a 40 / 41 a 60 / Más de 60»; stored as `monthly_cremations` = range top) and Rápido / Estándar / Completo (10/15/20, descriptions in `MODES` of `lib/diagnostics.ts`; `public_mode` = the preselected one; `GET` returns every active question with its `modes`, `POST /start` takes `mode`; local draft `vz_diag_public`) and lands on its private report `/diagnostico/informe/<public_token>` (`DiagnosticReportClient.tsx`, noindex): score, suggested plan with the price struck through and `promo_pct` discount (`promo_text`, both in Configuración), WhatsApp CTA to «Datos del SaaS» phone, PDF download (shared `components/diagnostics/DiagnosticPDF.tsx`, types in `lib/diagnostics.ts`). ## Infrastructure

- **Storage**: Cloudflare R2 (S3-compatible), client in `backend/app/utils/r2.py`
- **Media uploader**: `get_current_user` stores the user id in `db.info["current_user_id"]`; `MediaService.upload_media` saves it as `web_media_library.created_by` (migration `b9d1f3a5c784`; older files = NULL). Shown, with date/size/dimensions, in the SuperAdmin Biblioteca «i» panel (`components/admin/media/MediaInfoModal.tsx`); the public media list never exposes it.
- **Payments**: Polar.sh — set `POLAR_SERVER=sandbox` or `production`
- **Email**: SMTP via fastapi-mail (`backend/app/services/email.py`), account `no-reply@vinzer.cl` on Hostinger (`MAIL_SERVER=smtp.hostinger.com`, `MAIL_PORT=587` STARTTLS or 465 SSL, `MAIL_FROM_NAME` default «Vinzer»). Vinzer emails default Reply-To to the «Datos del SaaS» correo (info@vinzer.cl); crematorium-branded emails go out as «Crematorio X vía Vinzer» with Reply-To = the crematorium. Every email (signup, password reset, family notices, limit/AI/backup alerts, demo lead, memorial request + the family's confirmation) goes through `send_action_email` / `render_vinzer_email` (escaped text, optional `rows` table and `image_url`). Public forms (`/api/public/contact`, `/leads/demo`) only skip reCAPTCHA when `not settings.IS_PRODUCTION` (they used to check a non-existent `ENV` var, so anti-spam was off in production). Admin → Configuración → Datos del SaaS has «Enviar prueba» (`POST /api/internal/creator/config/test-email`). vinzer.cl DNS is on Hetzner: MX/SPF/DKIM/DMARC for Hostinger mail must be added there. Public form notifications (landing «Demostración guiada», memorial request) go to `notification_recipients()`: admin Configuración → Datos del SaaS → «Correo para recibir mensajes» (`sys_saas_config.notification_email`, up to 5 comma-separated, migration `d5f7b9c1e238`; never exposed publicly), falling back to `MAIL_FROM`.
- **Certificates**: PDF generation in `backend/app/utils/certificates.py` (~34KB, complex)
- **Audit**: All API requests logged via `backend/app/middleware/audit_middleware.py` to `AuditLog` table
- **Backups**: automatic backups run from a background task (`backend/app/services/backup_scheduler.py`): startup asyncio loop, 5-min check interval, `pg_try_advisory_lock` for exclusion across replicas. They no longer depend on HTTP traffic. Status writes to `sys_saas_config` need `apply_bypass_rls` (without it the UPDATE matched 0 rows, the status stayed `in_progress` and automatic backups never ran again); an `in_progress` older than 3 h is treated as interrupted. All `/api/internal/maintenance/backups/*` endpoints are **SuperAdmin-only** (`get_current_creator`; before, any tenant admin could download the full dump).
- **Restore check**: `app/services/backup_restore_check.py` restores the newest `backups/*.dump` from the R2 backup bucket into a temporary `<db>_restore_check` database (pg_restore, or `docker exec` into `BACKUP_PG_CONTAINER` when the binaries are missing), counts key tables, drops it and stores the result in `sys_saas_config.restore_check_*` (migration `d8a0c2e4f579`); monthly from the backup scheduler (only with automatic backups enabled and a successful backup), on demand via `POST .../backups/restore-check` (Admin → Configuración → Respaldos «Probar ahora»); emails `notification_recipients()` on failure.
- **API docs**: `/docs`, `/redoc` and `/openapi.json` are disabled when `ENVIRONMENT=production`
- **Error monitoring (Sentry, optional)**: backend `SENTRY_DSN` (`app/core/sentry.py`, also captures the 500s answered by `ErrorLoggingMiddleware` with their `correlation_id`), frontend `NEXT_PUBLIC_SENTRY_DSN` (build arg; `src/instrumentation*.ts`, `lib/sentryOptions.ts`). Empty = off. Never sends cookies, auth headers, bodies or URL query strings. `serverExternalPackages` keeps `@sentry/*` out of the server bundle (bundled, Turbopack emits a `node:inspector` chunk whose name breaks the standalone build on Windows).
- **Health**: `GET /api/internal/health` checks DB + Redis and returns 503 when one fails — point the external uptime monitor there.
- **AI balance alert**: `app/services/ai_balance.py` checks OpenRouter every 6 h (advisory lock 815002) and emails `notification_recipients()` + creates an admin notification when the available amount (min of account balance and the key's own cap) drops below `sys_saas_config.ai_balance_alert_usd` (default 2, migration `f9b1d3e5a472`) or the key stops answering; once per crossing (`ai_balance_alert_state`). Threshold edited in Créditos IA → Resumen (`PUT /creator/ai-credits/balance-alert`).
- **Deploy**: `./deploy.sh` on the VPS (pull, build, up, prune dangling images + build cache >72 h; never volumes). Compose sets log rotation (10 MB × 3) and `mem_limit` per container; Redis lives only on `db_internal` (no password, must not be on the proxy network).
- **Form Tokens**: Public registration forms use temporary tokens (`form_tokens`) with a 6-digit PIN and a few-day TTL. Generated from the tenant's Navbar "share" action.
